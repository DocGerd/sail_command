# ADR-0002: Pre-1.0.0, local-DB migration is low priority

## Status

Accepted — 2026-08-24.

## Context

SailCommand persists plans in IndexedDB (`app/src/services/db.ts`), and a
stored record can predate several schema additions made since it was
written. `app/src/services/migratePlan.ts`'s `migrateRequest` function is the
read-time normaliser for `PlanRequest`. As of 2026-08-24, reading it directly
confirmed it validates exactly three fields — `boat` (via `migrateBoat`),
`departureMs` (`typeof request.departureMs !== 'number'` rejects the record),
and `sailIds` (catalogue-checked against the migrated boat, or reconstructed
from the result's own sail list when the stored value is missing or
untrustworthy) — before returning:

```ts
return { ...request, sailIds, boat } as unknown as PlanRequest;
```

Every other member of `PlanRequest` — `origin`, `destination`, `viaPoints`,
`originHarborId`, `destinationHarborId`, `settings`, and any field added
later — passes through that spread completely untyped and unvalidated. The
trailing `as unknown as PlanRequest` cast makes this compile cleanly however
incomplete the runtime object actually is; nothing here forces a future field
to be handled.

This has already produced a recurring, real crash class: a component reads
one of those unguarded fields off a plan whose stored record predates it, the
value is `undefined`, and the read throws with no error boundary anywhere
under `app/src` to catch it — blanking the whole app rather than degrading
one component. Verified instances, all against the same mechanism:

- **PR #630** (merged 2026-08-20) — the marginal-depth-notice work that
  shipped alongside #624's items, in the same session, guarding a
  `plan.request.settings` read in `RouteSummary.tsx`'s new
  `MarginalDepthNotice` after a review round caught it blanking the app in
  the same shape.
- **#632** (open as of 2026-08-24) — `LiveView.tsx` reads
  `plan.request.settings.safetyDepthM` twice unguarded: the
  `const safetyDepthM = plan?.request.settings.safetyDepthM ?? null`
  binding (~:127), whose `?.` guards `plan` and not `settings`, and the
  `safety:` var of the `live.hts.depthCaution` `t()` call (~:345), a bare
  read plus `.toFixed(1)`. Its own text, verified 2026-08-20 at `095a04c`:
  "`app/src/services/migratePlan.ts` never validates `request.settings` —
  the string `settings` occurs zero times in that file." Re-confirmed
  against `develop` at `31c90d9` on 2026-08-24: still zero.
- **#654** (filed 2026-08-24, open as of that date) — `RouteSummary.tsx`'s
  `confinedWithin` memo spreads `plan.request.viaPoints` unguarded
  (`...plan.request.viaPoints` and `plan.request.viaPoints.map(...)`), which
  throws `TypeError: ... is not iterable` on a stored record that predates
  `viaPoints`. `viaPoints` does not occur anywhere else in
  `migratePlan.ts`.

Each of these is the same shape recurring at a different call site: a field
`migrateRequest` never validates, read unguarded downstream, on a record old
enough to lack it.

PR #624 (merged 2026-08-20) is adjacent and deliberately NOT counted above,
because counting it would inflate the evidence for this decision with a
different mechanism. Its `migratePlan.ts` item tightened a field
`migrateRequest` already validates — `sailIds` gained a catalogue
cross-check, so a foreign or stale sail id can no longer reach
`planRoute.ts`'s `polarFor` and its named `#54: no polar table for ${key}`
throw. That is under-validation of a checked field — the trigger is a stored
`sailIds` value that is wrong, which the code's own comment attributes to "a
foreign/imported record", not a record that LACKS the field — and it surfaces
as a named throw rather than an undefined dereference. Its `App.tsx` item is
a wrong-SOURCE read — the `<DepthProfile>` call site passed the live
`settings.safetyDepthM` instead of `plan.request.settings.safetyDepthM` —
whose symptom was an understated shallow-exposure figure, not a crash. That
one is an instance of the fabricated-value hazard the boundary section below
is about, not of this one.

## Decision

Until version 1.0.0, migrating local IndexedDB data is a LOW PRIORITY. The
maintainer's own words, verbatim: "Until achieving version 1.0.0 it is only
low priority to migrate local DB stuff. So if there is some migration issue
and fixing it might not be feasible, just mark it as a breaking change in
the changelog and skip doing migration magic."

Concretely: when a stored-record problem surfaces and a real fix — teaching
`migrateRequest` (or a sibling normaliser) to actually validate and migrate
the field in question — is not feasible, the sanctioned outcome is to
declare a BREAKING CHANGE in the changelog and let the affected records stop
being readable as plans, rather than building migration machinery to carry
them forward. "Stop being readable" is the existing behaviour, not a new
one, and it is not deletion: `migratePlan` returning `null` already means
`services/db.ts` lists that record as unreadable and leaves its bytes
untouched (`migratePlan.ts`'s own header: "A null NEVER means 'delete'").
Nothing in this ADR sanctions deleting a user's stored records.

## The boundary that makes this safe

This is the most important part of this decision, and it is narrow on
purpose.

**This ADR waives migration machinery. It does NOT waive defensive reads.**
A cheap read-site guard — the #614 / #632 shape: validate the field, or fail
closed, at the point where it is read — stays correct, stays expected, and
is not what this decision is about. `migrateRequest` choosing not to
reconstruct a missing `viaPoints` list is in scope for this ADR;
`RouteSummary.tsx` spreading `undefined` with no guard at all is not — that
is an ordinary defensive-programming bug, independent of any migration
question, and must still be fixed.

And failing closed must never mean falling back to a fabricated default. On
the on-water hazard path — anything a safety reading (depth, exposure,
route confinement) depends on — a confident wrong number is worse than an
absent one. Silently substituting a plausible-looking default for a missing
field is not an acceptable way to "handle" a migration gap; it trades a
loud, honest failure for a quiet, wrong one. That constraint is independent
of this ADR and is not relaxed by it.

## Consequences

- When a contributor hits a stored-record problem pre-1.0.0 for which no
  migration is feasible, they should still add a cheap guard at the read
  site (fail closed, never fabricate), then write a
  `changelog.d/<n>.changed.md` fragment stating plainly that saved plans
  from before version X are not carried forward and will need to be
  re-planned.
- A record that stops being readable must be surfaced honestly to the user —
  an unreadable plan should read as unreadable, never silently vanish or
  silently render with fabricated data standing in for what was lost.
- This decision does not retroactively excuse #632 or #654, or any other
  open unguarded-read issue: those are read-site defensive-programming bugs
  in scope regardless of this ADR, and the cheap-guard fix remains the
  expected and preferred outcome for them.

## Considered and rejected

**Build out full field-by-field migration in `migrateRequest` now**,
covering every `PlanRequest` member as each new one is added. Rejected as
disproportionate pre-1.0.0. The maintainer's ruling gave no reasons beyond
the priority call quoted above; what follows is this ADR author's reading of
why it is a proportionate call, recorded so a future session can re-examine
the reasoning rather than inherit it as a ruling — the user base is small,
stored plans are inexpensive to recreate, and the app has no backend and no
external clients depending on long-term read compatibility of its local
storage format. Revisit this once real users carry real saved plans across
versions.

## Revisiting this

Reopen this decision at v1.0.0, once real users have real saved plans that
need to survive upgrades — the version boundary is the maintainer's own; the
cost/benefit argument for it here is this ADR author's. Migration debt that
was cheap to defer while adoption was low becomes expensive to defer once
users have plans worth preserving, so `migrateRequest` should be revisited
for genuine field-by-field validation and migration rather than the
breaking-change path this ADR sanctions.
